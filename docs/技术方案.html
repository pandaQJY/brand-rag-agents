00摘要

为什么这两件事应当是一个系统

「用 RAG 写营销内容」与「用多 Agent 诊断官网」拆开各做各的，都能跑通。 但拆开会丢掉三处能力——它们不是把两个项目并排放置就能得到的， 而是只有当两条链路共享同一个知识库与同一套检索时才成立。

本方案的一条主线

凡能用确定性方法裁决的，就不该交给模型。 这条判据在系统里出现了五次：引用编号校验、数字比对、结构扫描、依赖拓扑排序、大纲小节数校验。 每一次的收益都相同——零成本、零波动、结果可复现。 它也解释了本方案的大部分取舍：为什么不用框架、为什么输出不用 JSON、 为什么核查要分层而不是交给一次大模型调用。

01总体架构

两条链路，一套检索

系统有两个数据源、两份语料、一套检索、两条消费链路。 关键在于中间那一层是共享的——正因如此，右侧两条链路才能互相供给， 形成图中标为 ①②③ 的三处咬合。

一句话读懂三处咬合

① 审计标准：拿品牌自己写的方法论，去审它自己的官网。
② 原文问答：分析型 Agent 答不了「官网上这句话怎么说的」，检索能。
③ 策略回灌：诊断说该补什么，写作链路直接把它补出来。

02知识库

把设计稿变成可引用的知识资产

品宣稿是设计稿，不是文档。它的信息大量藏在图表、流程图、数据看板里， 而 PDF 的文字层只能捞到其中一部分。因此解析必须双通道，且两路产物分开存放不提前合并—— 事实核查时需要知道某条陈述来自可提取文字还是来自图像转写。

切分：为什么以页为单位

幻灯片本身就是设计好的语义块，页码天然是引用锚点。在此之上做两件事： 识别分节页（带大号装饰序号、自身几无内容）并入其后一页，避免产生「只有一个标题」的噪声单元； 把分节页标题作为章节名向后传播，让每个单元都带章节上下文。

这个决定的代价

以页为单位在多数情况下成立，但一个论点跨两三页展开时，单页单元会丢失上下文。 当前靠「章节名向后传播」缓解，不彻底。后续方向是父子单元：检索用页级， 喂给模型时带上同章节的相邻页。

站点语料为什么反过来，按 h2 分节

网页不是幻灯片，一篇 5,760 字的 Blog 是连续文档。整页做成一个单元能命中它， 却无法指出「答案在哪一段」——而站点语料的用途恰恰是回答「官网上关于 X 是怎么说的」。

实测依据很具体：首页 3,508 字、62 个标题，其中就包含「GEO 与 SEO 的区别」那组 FAQ。 整页一个单元时它被淹没在另外六十多个标题里；按 h2 切开后成为独立单元，检索可直接命中。 52 页最终切成 193 个单元，26 页被切成多节。

03检索

混合检索与它的评测陷阱

向量（bge-small-zh + FAISS）与 BM25（jieba 分词）两路并行，用 RRF 融合而非加权求和： 余弦相似度落在 [0,1]，BM25 分数无上界且随语料波动，两者量纲不同，加权必须先归一化， 而归一化系数会随语料变化失效。RRF 只看排名不看分数，无需调权重。 

RRF(d) = Σ 1 / (k + rankᵢ(d))     k = 60（惯例）

k 的作用是压低头部名次的绝对优势，使「在两路都排中游」的文档能胜过「只在一路排第一」—— 这正是混合检索想要的行为。

评测本身的不足

两组合计 25 条人工标注查询，规模仍偏小：高难度集单条查询权重高达 11%， 一次标注错误就会明显移动分数。当前唯一未命中的是「怎么衡量优化之后有没有效果」—— 期望产品监控页，实得三个相邻页。这类「问效果、答案在产品页」的跨语义查询是现有两路都不擅长的。

语料抽象：一套检索服务两份语料

检索层不认识具体的语料类型，只依赖一个协议——「有 chunk_id、 能给出 index_text()、能报出自己的引用锚点」。 知识库单元与站点单元各自满足它，因此新增第三份语料（如客户案例库）只需再声明一个 Corpus， 检索代码一行不改。

一处刻意的降级

向量索引缺失时降级为纯 BM25 而非报错。理由是两条路的成本不对称： BM25 在内存里现建即可，向量索引需要先跑一次构建。 只抓了官网还没建索引时，原文问答仍应能回答问题——检索质量下降，但功能不塌。 降级会打印提示，不静默。

04幻觉控制

四层半拦截，其中三层不调模型

内容生成的第一约束是不得编造知识库里没有的公司事实、客户案例、数据或技术指标。 仅在 Prompt 里写「不要编造」是不够的——那是请求，不是约束。

为什么单独设第 3.5 层

  1. 数字是幻觉最危险的载体。A/B 实测中，对照模型把证据里的「61.66 亿」写成「80 亿」， 并凭空造出「300%」——句子读起来专业、还挂着真实的引用编号，人眼极难发现。
  2. LLM 核查器对数字不可靠。实测同一篇文章两次核查结果不同（1 条 vs 5 条），存在采样波动。
  3. 这件事本不需要模型。数字要么在语料里逐字出现，要么没有。 一次 in corpus 判定即可，零成本、零波动、无漏报。
这一层已知的边界

它分不清「跨证据推算」与「凭空编造」。模型把某两页里 Top 6 的月访问量加总得出「超 80 亿」， 第 3.5 层判编造（语料中查无此数），第 4 层判有据支持——两层结论相反。 实际情况是模型做了一次加法，数在事实上正确，但确实不是语料里的原话。

当前处置是标出来交给人判断，不自动改写：幻觉控制场景下宁可多报不漏报。 两层结论矛盾本身不是缺陷，而是设计意图——如果两层永远一致，其中一层就是多余的。

选型也是幻觉控制的一部分

生成模型固定大纲与证据下的表现结论
qwen-max套话多，且违反 Prompt 明令禁止的「本文将探讨」句式未选
qwen3-max开篇即上带引用的硬事实，事实纪律良好选它
deepseek-v3文笔最佳，但把 61.66 亿写成 80 亿、凭空造出 300%未选

第一优先级是不得编造数据，因此选事实纪律而非文笔。选型配置按环节分离，改模型不动业务代码。

05调度

路由的产物不是「选中一个 Agent」，而是一份执行计划

这是「简单写多个 Prompt」与「真正调度」的分界。 调度分三层，同样遵循确定性优先：能用规则解决的不调模型，能用代码推导的不问模型。

追问缓存的正确性判据

连续追问时编排器复用板上已有结果，这个优化成立的前提是该 Agent 的产出与用户问什么无关。 分析型 Agent 满足——它们只通读官网、输出固定小节，换个问题结论也一样。 但原文问答与整合收口不满足：它们的输入里就含用户的问题，复用上一轮等于答非所问。

把判据放在正确的位置

这条判据声明在 Agent 类上（question_dependent），而不是硬编码在编排器里。 因此新增 Agent 时只需如实声明自己是哪一类，调度与界面自动跟上—— 不需要有人记得去另一个文件里补一行 if。

06咬合点

三处只有合并后才成立的能力

① 审计标准：拿品牌自己的方法论去审它自己

诊断官网最难的不是找问题，是让结论站得住。初版写「官网无 JSON-LD，AI 无从识别实体」—— 这站不住，大模型读纯文本毫无障碍，JSON-LD 对 AI 检索管线的加权作用并无公开确证。

换判据之后

品牌方自己的方法论把 JSON-LD 列为 GEO 网站基建的首要能力 （品宣稿 P29），而官网 52 页覆盖率为 0。

这不是「我建议你加 schema」，而是「按你们自己写的标准，官网没做到」—— 除非承认方法论有问题，否则无法反驳。实测抽出 4 条标准，升格 3 条结论为 A 档。

② 原文问答：补上一条本该存在的路径

原有四个 Agent 全是「通读全站 → 输出固定小节」的分析器，答不了指向具体内容的问题。 问「GEO 和 SEO 有什么区别」时，路由只能指向官网信息分析，而它的八个小节里没有一节是 「官网对某个概念是怎么讲的」——答案就在已抓取的页面里，系统却没有路径把它取出来。

补上这条路径需要的正是检索能力，而知识库链路已经有一套实测过的混合检索。 把它指向站点语料，缺口即被填上：检索定位到具体小节 → 模型据此作答 → 标注页面 URL 供人核对。

③ 策略回灌：让建议变成可发布的初稿

写不了的要说清为什么写不了

13 条策略建议里有 3 条被主动跳过：两条「案例页」因知识库没有客户案例的细节事实， 硬写只会得到泛泛之谈；一条「元数据修改」根本不是文章，是改 meta 标签的工程任务。 把不可写的项也塞进流水线，只会得到一堆需要人逐句删改的稿子，那比不生成更糟。

07工程判断

确定性优先，以及它的五次应用

应用处本可以交给模型改为代码裁决后
引用编号校验（第 3 层）让模型自查引用对不对比对本次证据集，编号不存在即判捏造
数字比对（第 3.5 层）让核查器判断数字是否属实逐字比对语料，无漏报、无采样波动
结构扫描（B 档诊断）让模型看页面判断结构好坏title 唯一性、JSON-LD、h1 数、alt 缺失率直接测
依赖补齐与排序让模型决定先调用谁静态声明 + 递归展开 + 拓扑排序
大纲小节数校验相信模型遵守 Prompt 里的数量约束按规格区间校验并重试一次
最后一条是跑了两次才发现的

同一条 FAQ 指令两次规划，一次 7 个问题、一次 3 个，而规格明写「6–10 个问题」—— 模型违反了自己收到的约束，而系统毫无察觉，直接拿 3 节的大纲跑完了整条链路。 数量是纯确定性判据，本就不该由模型裁决。

处置强度也需要判断：重试一次而非报错。小节偏少只影响完整度不影响正确性， 为此中断整条链路不值当；重试仍不达标就带警告继续，把判断留给人—— 与第 3.5 层「标出来交给人」的处置一致。

为什么不用 LangChain / LlamaIndex / CrewAI

  1. 幻觉控制是本方案重心，而这是框架封装最薄的一环。 四层半里三层是自写的确定性校验，用框架反而要绕开它的默认链路。
  2. 「大纲先行、分节检索」不是框架的默认形态。 RetrievalQA 是一次检索一次生成，要改成每节自带查询各自检索，等于绕过框架自己编排。
  3. 调度逻辑本身就是要展示的东西。DAG 只有 6 个节点、依赖静态可知， Agent 基类约 90 行、路由约 130 行。用框架的 Crew/Graph 把调度包起来， 展示出来的是「会配置框架」而非「会设计调度」。
  4. Prompt 需要逐字可控。四种内容类型的结构规范要分别注入大纲与生成两个 Prompt， 框架的模板层反而是阻碍。

不用框架不等于不会用框架——这是规模判断，不是能力边界。

输出一律行式，不用 JSON

实测本项目所用模型在嵌套结构上不可靠（漏方括号、吐垃圾片段）， 而 ## 小节名 + 每行一条的记录块式文本解析确定且零失败。 这条结论先在写作链路得到验证，后被 Agent 链路沿用。

08不足

已知边界与后续方向

按影响排序。第一条是当前最危险的，因为它绕过了全部拦截机制。

不足影响后续方向
视觉转写质量无法自动校验 模型若把图表里的数字看错，下游全部环节继承该错误，而四层半拦截查不出来——它对照的正是这份已经错了的语料 对含数字的页做双模型交叉转写，不一致处标记待人工确认
第 3.5 层分不清推算与编造 跨证据做加法得到的正确数字会被判为编造 对 missing 的数字追加一次「能否由证据中的数经简单运算得到」的定向检查
评测集仅 25 条人工标注 高难度集单条权重 11%，一次标注错误明显移动分数 扩到 50+ 条，补跨页论述与多跳问题
大纲只校验数量，不校验覆盖面 7 个问题也可能全都围着同一件事打转 比对大纲与资料库目录的覆盖度，对未被触及的章节给出提示
知识库仅支持单文档 多文档需要引用格式带文档标识与跨文档证据冲突处理 站点语料侧已走通多语料抽象，知识库侧照此跟上
Agent 依赖为静态声明 无法按问题动态调整依赖强度 引入可选依赖：上游证据已充分时跳过前置环节
客户问题生成无真实验证 生成的问题是模型模拟，未与真实搜索数据比对 接入真实 AI 平台提问测试，验证官网是否真的被引用
抓取为单次快照 官网更新后需手动重抓 记录 ETag / Last-Modified 做增量更新与变更对比

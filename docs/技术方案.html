01摘要

系统概览：一份品宣稿支撑的两条链路

系统围绕一份品牌品宣稿展开：先把它构建成可检索、可引用的知识库， 再由两条链路共享这份知识库与同一套检索——一条对外生成内容，一条对内诊断官网。 共享是设计前提，不是结果：正因为两条链路吃的是同一份语料、 走的是同一套检索，它们才能互相供给，形成 §10 的三处咬合。

4条标准
从品宣稿抽出的品牌自述标准，把 3 条诊断结论升格为「按你自己的方法论应做到而未做到」
0.741MRR
高难度查询集上混合检索对纯向量的 0.593，Hit@1 66.7% 对 44.4%
31处引用
策略建议自动成稿，覆盖 19 页、0 处捏造引用、13 个数字逐字命中语料
本方案的一条主线

凡能用确定性方法裁决的，就不该交给模型。 这条判据在系统里出现了五次：引用编号校验、数字比对、结构扫描、依赖拓扑排序、大纲小节数校验。 每一次的收益都相同——零成本、零波动、结果可复现。 它也解释了本方案的大部分取舍：为什么不用框架、为什么输出不用 JSON、 为什么核查要分层而不是交给一次大模型调用。

系统有两个数据源、两份语料、一套检索、两条消费链路。 关键在于中间那一层是共享的——正因如此，右侧两条链路才能互相供给， 形成图中标为 ①②③ 的三处咬合。

一句话读懂三处咬合

① 审计标准：拿品牌自己写的方法论，去审它自己的官网。
② 原文问答：分析型 Agent 答不了「官网上这句话怎么说的」，检索能。
③ 策略回灌：诊断说该补什么，写作链路直接把它补出来。

结论一 · 视觉转写是必需项，不是加分项

平均每页 278 字意味着仅做文字提取会丢失约一半信息量，生成的 Blog 必然空洞且缺乏事实支撑。 方案采用文字层 + 视觉转写双通道解析。

结论二 · 以「页」为语义单元切分

幻灯片本身就是设计好的语义块，页码天然是引用锚点。这同时解决了切分质量与引用溯源两个问题。

结论三 · 语料很小，但仍要认真做检索

全文约 1 万 token，技术上完全可以整篇塞进上下文而不做检索。本方案仍实现完整检索链路， 理由是可扩展性（品宣册会增补）、引用精确度（页级定位优于全文定位）与成本控制。 这一点在 README 中会主动说明——诚实描述边界比假装语料很大更有说服力。

03知识库构建

把设计稿变成可引用的知识资产

系统分为两个独立运行的阶段。离线阶段把 PDF 转化为带页码锚点的知识库，产物落盘持久化； 在线阶段消费这个知识库完成写作。两者通过 chunks.jsonl 与索引文件解耦—— Demo 启动无需重跑解析，解析质量也可直接查看。

3.1 双通道解析

每一页同时走两条通道，结果合并为一个 PageDoc：

  • 文字通道——PyMuPDF 提取文字块并保留坐标，按位置恢复阅读顺序，避免多栏排版串行错乱。
  • 视觉通道——每页渲染为 150 DPI 的 PNG，送 Qwen-VL-Max 做结构化转写。
已实测验收 · 全 42 页

视觉通道产出 21,317 字符，文字层 10,738 字符—— 知识库 66% 的内容来自视觉通道。增益最大的 P32（产品监控系统页） 文字层仅 77 字（六条光秃标签），视觉转写补回 1,382 字：仪表盘指标 AI Visibility 76.23%、 竞品分析表字段、内容生成流程。全量转写耗时 2 分钟， 消耗 86,704 输入 / 10,914 输出 token。

Prompt 约束

视觉转写的 Prompt 必须明确要求「只描述图中确实存在的内容，不推断、不补全、不美化」。 转写环节是幻觉的第一个入口——如果 VL 模型在这里就编造了数据，后续所有核查都会失效， 因为核查器比对的正是这份转写结果。

3.2 切分策略

以页为基本单元，但不机械地一页一块：

  • 标题页、过渡页（文字极少且无实质内容）并入后一页，避免产生噪声 chunk。
  • 连续同章节页（靠标题模式识别）合并，chunk ID 记作 P12-13。
  • 每个 chunk 保留 page_no、title、text_layer、vision_text 四个字段分开存储，核查时可精确定位事实来自文字层还是图。

04检索与生成

混合检索、大纲先行与分节证据

4.1 为什么不能「一次检索」

这是本方案最重要的设计决策。一篇 Blog 的不同小节需要 PDF 里完全不同的段落—— 「什么是 GEO」和「万悉的服务能力」检索目标毫无重叠。用主题做一次检索， 必然是所有小节共享一份平庸的证据集，顾此失彼。

已实测验证 · 大纲先行跨过了纯语义鸿沟

§4.4 评测中唯一未解的查询是「怎么衡量优化之后有没有效果」——检索返回 P36/P37/P30，始终召不回监控系统页 P32。用户说「衡量效果」， 页面写「AI可见性监控」，字面零重合、语义也没拉近。

走大纲先行链路后，规划器把它改写成 「Trendee GEO 监控系统 实时追踪AI可见性变化」， P32 以向量#1 + BM25#1 被召回。这是本方案核心设计的直接验证。

关键实现：把资料库目录交给规划器

规划器之所以能改写出贴合材料的查询，是因为它看得见一份资料库目录 （编号 + 章节 + 标题 + 正文开头两行，共约 2,800 字符）。没有这份目录， 模型只能凭主题臆造查询。

踩坑 · 标题不等于内容索引

目录最初只放标题，结果「什么是 GEO」一节召不回 P12—— 而 P12 是全篇唯一定义了「GEO（生成式引擎优化）」的页。原因是它的标题 《GEO时代到来：AI投毒乱象》完全没有广告自己含有定义。

修法很轻：把正文开头两行也放进目录。P12 的正文首行恰是 「什么是GEO ？」。补上后规划器直接生成该查询，P12 召回成功。 零 API 成本、纯确定性。

踩坑 · 没有证据的环节不能碰事实

规划阶段最初会写带事实的导语，结果模型每次都给 GEO 编一个不同的英文全称： Global Exposure Optimization / Generative Enterprise Optimization / Generative Engine Optimization——只有最后一个是对的。 而材料 P12 明确写着「生成式引擎优化」。

根因是设计漏洞：让一个手里还没有资料的模型写了事实。 现在 Prompt 明令规划阶段不得产出定义、数字、人名、功能清单， lead 只写「导语应当覆盖什么」。这条推广开来是一条通则—— 流水线里任何尚未拿到证据的环节，都不得触碰事实。

4.2 混合检索与 RRF 融合

每个 query 同时走向量与关键词两路，各得一份排序列表，再用倒数排名融合（RRF）合并。 RRF 只依赖排名而非分数，因此不需要在语义相似度与 BM25 分数之间做量纲归一化—— 这是它在工程上比加权求和稳定得多的原因。

原假设是「证据给多了模型会挪用 → 风险声明随 k 上升」。 实测风险声明为 0 / 0.5 / 0 / 0 / 0.5——无任何趋势， 在每个 k 仅 2 个样本的量级下属于纯噪声。该假设不成立， 本次调优未能得出质量维度的结论。

唯一呈单调规律的是证据利用率，且它是机械性的、不受生成随机性影响： k=3 时 22% 的检索证据未被引用，k=8 时这一比例达到 54%—— 检索了、付了 token、模型读了，然后没用上。

决定：维持 k = 4

依据不是「4 最优」，而是数据不支持改动：质量维度在 k=2–8 全程平坦， 利用率倾向 k=3，而 k=3 的文章字数又是最低的——两个维度指向不同方向， 且样本量仅 2 主题 × 1 次。基于噪声修改一个站得住的默认值， 比保留它更糟。

实验仍有正面收获：流水线在 k=2 至 8 全程未出现质量崩塌 （通过率 96–100%）。结合核查器已通过负向验证，说明幻觉控制在整个参数区间 都在生效，而非依赖某个特定配置侥幸成立。10 次运行中另有 1 次捏造编号被第 3 层拦下， 是纯代码层在真实运行（而非注入测试）中的一次实际拦截。

4.4 检索质量评测

检索改动如果只靠翻几条结果判断好坏，很容易自我欺骗。因此建了一套 人工标注的评测集（retrieval/eval.py），任何改动都能量化比较。 标注方式是逐页阅读品宣稿，为每个查询标出确实含有答案的页。

第一版评测集失败了

最初 16 条查询大多贴近页标题，结果三路 Hit@5 全是 100%， 混合检索与纯向量分数完全相同——看不出任何差异。 一个满分的评测集比没有评测更危险：它会让人得出「混合检索没有价值」的错误结论。 于是补了第二组高难度查询：主题式宽问题（与任何标题都不字面重合）+ 专名查询。

4.3 生成环节的 Prompt 约束

  • 凡涉及公司事实、客户案例、数据、技术指标的陈述，句末必须挂 [Pxx] 标记。
  • 证据集中没有的信息一律不写；某节证据不足时，明确输出「资料不足」而非补全。
  • 行业通识（如「GEO 即生成式引擎优化」）可不挂引用，但不得冒充为万悉的独有事实。
  • 输出结构固定：标题 → 导语 → 小标题分节 → FAQ（可选）→ 结尾。

评测：一个满分的评测集比没有评测更危险

语料抽象：一套检索服务两份语料

检索层不认识具体的语料类型，只依赖一个协议——「有 chunk_id、 能给出 index_text()、能报出自己的引用锚点」。 知识库单元与站点单元各自满足它，因此新增第三份语料（如客户案例库）只需再声明一个 Corpus，检索代码一行不改。

一处刻意的降级

向量索引缺失时降级为纯 BM25 而非报错。理由是两条路的成本不对称： BM25 在内存里现建即可，向量索引需要先跑一次构建。 只抓了官网还没建索引时，原文问答仍应能回答问题——检索质量下降，但功能不塌。 降级会打印提示，不静默。

05幻觉控制

四层半拦截，其中三层不调模型

本链路的第一约束是「不得编造 PDF 中没有的公司事实、客户案例、数据或技术指标」。 仅在 Prompt 里写「不要编造」是不够的——那是请求，不是机制。 本方案用四层半逐级收紧的拦截链路，其中三层是纯代码——零 API 成本、零采样波动。

已实测 · 核查器通过负向验证

干净文章的核查通过率是 100%——但这个数字本身不能作为证据， 一个从不报错的核查器和一个满分评测集是同一个陷阱。因此向文章注入 4 条已知幻觉：

注入的幻觉判定核查器给出的判据

4 条全部抓出，零漏报。两点尤其关键：数字篡改被精确指认 （没有因为「80% 和 20% 都像百分比」而放过）；最后一条完全没有引用标记， 第 3 层对它是瞎的，第 4 层照样揪出——这正是设立第 4 层的核心理由。

一个意外的正面信号

生成的文章里写了「同义千问」（应为通义千问）。初判为模型笔误， 核对后发现材料 P08-09 里原本就是「同义千问」——视觉转写忠实照抄了 品宣稿的错字，生成环节也没有自作聪明地纠正。 对这个系统而言，忠于原文比文字正确更重要。

第 3.5 层：数字的确定性校验

这一层是后来补上的，起因是一次模型 A/B 实测：deepseek-v3 把证据里的 「61.66 亿」写成「80 亿」，并凭空造出「300%」——句子读起来专业、还挂着真实的引用编号， 人眼极难发现。

促使它独立成层的，是两个观察：

  1. LLM 核查器对数字既不可靠也不稳定。 实测同一篇文章两次核查得到 1 条与 5 条风险，存在采样波动； 且它漏掉过「22.3%」这个语料中不存在的数字。
  2. 这件事本来就不需要模型。 数字要么在语料里，要么不在。确定性比对零成本、零波动、无漏报—— 凡能用确定性方法裁决的，就不该交给模型。

实现上并非简单的字符串包含（那会被 US8380607 里的「80」骗过）， 而是数值化比较：把「61.66亿」解析成 (61.66, "亿")， 再判断文中数值是否为语料中某个同单位数值的四舍五入。

判定含义实例
exact逐字命中语料17.6%、20+
approx同单位数值的取整（容差 2%）文中 61亿 ← 语料 61.66亿
missing语料中不存在该数值80亿、300%、22.3%
这一层的固有边界：只管数值，不管归属

它校验的是「语料里有没有这个量级的数」， 而非「这个数说的是不是这件事」。 实测中「4万余次会话」曾因撞上语料里不相干的「$5万亿 全球AI电商市场规模」而被判成立。 收紧量级（只接受同数量级内的支撑）解决了该例，但根本问题仍在—— 归属判断是第 4 层的职责，只有 LLM 能理解语义绑定。

这是有意保留的边界：把实体绑定塞进本层会引入语义判断， 也就引入采样波动，恰好毁掉它「零成本、零波动、无漏报」的核心价值。两层分工，各守其职。

下界表述必须与编造区分

真值 3.45 亿时，「月活超3亿」是成立的保守表述，而「月活 3亿」是不准确的精确声明。 初版把两者一并判为编造，属于误报——而误报比漏报更伤演示可信度： 读的人会看到明明写对的句子被标红。现已识别 超/突破/逾/余/不低于 等修饰词， 此时只要语料存在同单位且不小于该值的数，即判成立。

调试记录：同一个错误犯了两次

字面命中最初写作 val in corpus，导致「4万」命中语料中的「834万」。 我在处理「80亿」时已经想到过子串问题，却只在近似匹配那条路径上加了防护， 字面匹配这条漏了——同一个文件里同一类错误犯了两次。 现两条路径都要求数字边界 (?<![\d.])…(?!\d)。

实测：抓到了 LLM 核查器漏掉的一条

对含已知编造的文章运行，第 3.5 层抓出 80亿、300%、22.3% 三条编造， 其中 22.3% 是 LLM 核查器完全漏掉的；同时把「61亿次」正确判为取整 （语料原值 61.66亿）而非编造。两层互补，不是重复。

边界：检测之后该怎么办

当前系统只检测、不处置——Demo 中风险声明标黄标红后即交由人工判断。 这是一条明确的边界，也是下一步最值得做的加固。设计已经想清楚，未在本次实现。

关键在于：四类判定的可修复性完全不同，不能一刀切。

判定能否自动修复处置方式
contradicted 数字或主体错误 能 证据中存在正确值，直接替换。如「80%」→「20%」
miscited 引用指错页 能 事实为真，仅编号有误，改写引用编号
unsupported 无依据 不能修，只能删 材料中根本没有，「修」等于再编一次；删除该句或降级为不含该事实的表述
事实为真但漏标引用 能 补上对应引用编号

三条必须守住的原则

  1. 只替换受影响的句子，绝不重写全文。 全文重写会丢掉已验证通过的内容，并引入一批新的幻觉——等于推倒重来，不收敛。
  2. 修复后必须重新核查。 修复本身也是一次生成，同样可能产生幻觉。不复查的修复等于没修。
  3. 必须设轮次上限（建议 2 轮）。 超出仍有风险则停止，标注为「需人工处理」—— 系统承认自己搞不定，比假装修好了更安全。
修复能力的上限是证据质量

有一类幻觉这套机制根本修不了：若视觉转写阶段就把数字读错， 核查器会判定文章「有据支持」，修复器更不会触碰它。 错误在证据层时，下游全部失效。 因此提升转写准确率的优先级，高于加强下游修复。

06上下文构建

9.6 万字，怎么进一次 Prompt

全站正文 96,327 字，而模型单次调用的上下文是 3 万 tokens 量级。 所以问题从来不是「装不装得下」，而是丢什么、怎么丢。 这一节决定了后面每个 Agent 看得见什么，也就决定了它们的结论站不站得住—— 一个看不见证据的 Agent，Prompt 写得再好也只是在猜。

先看一次真实翻车

系统曾判出「官网缺少解释 GEO 与 SEO 区别的 FAQ」， 并据此给出一条内容补充建议。而万悉官网首页就有一整块 FAQ， 第一条正是「GEO 到底是什么？和 SEO 有什么本质区别？」。 同一次输出还判了「官网没有白皮书」，而 /geo-center/whitepapers 下挂着三份。

错不在模型，它确实没看见——因为上下文没给。 三层原因叠在一起，每一层单独看都像无关紧要的实现细节。

第一层：标题文字从不进正文

抓取时正文由 body.find_all(["p", "li"]) 拼成， 标题标签的文字一个字都不进 text。 而首页 FAQ 的问句写在 <h3> 里、答案写在 <p> 里—— 送进模型的于是是一串没有问题的答案， 孤立读来像营销段落，根本读不出这是一组问答。

改为按文档顺序抽取块级元素、并保留 # 层级标记后， 模型不只看得见标题，还看得出谁统辖谁。

第二层：每页正文都混着全站模板

每页开头四条 🎉 公告条（同一条重复两遍）、结尾电话邮箱备案号，合计 200 余字。 对 /geo-center/whitepapers 这种全页 382 字的页面， 模板占了一半以上——送进模型的样本里，真正属于这一页的内容反而是少数。

判据直接沿用结构扫描里已经验证过的那条：出现在超过半数页面的行是模板，不是内容。 同一条主张在抓取层与诊断层各用一次，不必维护两套逻辑。 剔除而不丢弃——模板里有 slogan 和公告，那是品牌表达的一部分， 因此单独存档，在上下文里露一次面。

第三层：覆盖靠抽样，而抽样保证不了「有没有」

前两层修完，正文仍要压缩——原方案按板块抽样，8 页给正文、其余只给标题。 问题在于 GEO 诊断 Agent 被要求回答「官网还缺什么」， 那是对全站下的断言，而它手上只有几篇正文样本。 样本里没有，不等于站上没有。 预算调多大都堵不住这个洞，因为它是结构性的。

解法不是把样本调大，是换个东西来回答这类问题——站点自己写的标题目录。 全站 421 条 h1–h3 渲染成大纲约 16.5k 字，比只覆盖 8 页正文的样本还便宜， 却让 52 页全部露面。正文样本就此退居辅助：它只需回答「这个站怎么说话」， 那本来就只要几篇代表作。

由此定下的三条规则

规则做法它防住的是什么
覆盖靠大纲，不靠抽样 全站 h1–h3 目录整体给出，凡要对全站下断言的环节（GEO 诊断、用户问题生成）都拿到它；Prompt 里配硬约束：断言缺失前必须先在大纲里搜一遍 把「样本里没见到」误报成「官网没有」

降级时问句标题一律豁免

预算不够时按「标题截到 60 字 → 截到 30 字 → 只留 h1–h2 → 只留 h1」降级， 少看几层结构，每页仍然看得见；砍页面则整页凭空消失。 但问句式标题（以 ？/? 结尾）在任何层级都保留。

这不是为这个站开的后门——对 GEO 分析而言，问句标题是价值最高的结构信号， 它直接对应「客户会问什么、官网答没答」。首页那组 FAQ 恰好写在 h3 上， 按层级一刀切，头一个丢的就是它。

站点语料的切分：为什么反过来按 h2 分节

知识库以页为单位，因为幻灯片本身就是设计好的语义块。网页不是——一篇 5,760 字的 Blog 是连续文档，整页做成一个检索单元能命中它，却无法指出答案在哪一段，而站点语料的用途恰恰是回答「官网上关于 X 是怎么说的」。

07Agent 设计

调度是核心，Agent 是执行单元

本链路的成败线在于一句话：不能只是简单写多个 Prompt，必须体现 Agent 调度逻辑。 把四个 Prompt 串起来叫不上多 Agent 系统。 真正的分野在于——用户只说一句话，系统自己推导出该调用谁、按什么顺序、如何传递中间结果。

本链路实现四个能力 Agent—— 不是为了凑数，而是因为只有四个才构成真实的依赖关系： 诊断必须先知道品牌在说什么，模拟客户提问必须先知道服务对象是谁， 内容策略必须同时吃到诊断结果与客户问题。少任何一个，DAG 就退化成并列调用。

6.1 共享状态而非参数传递

Agent 之间不直接调用彼此，而是统一读写一块共享状态（Blackboard）。 这样做有三个具体收益：

  • 连续追问可复用。用户追问「那 FAQ 该怎么写」时， SiteAnalyst 与 GeoAuditor 的结果已在 Blackboard 中，无需重跑。
  • 中间结果可展示。多 Agent 系统最难调试的就是「中间发生了什么」， Blackboard 天然就是这份数据的容器。
  • Agent 之间解耦。新增 Agent 只需声明它读什么、写什么，不必修改既有 Agent。

6.2 GEO 诊断分两层做

§01 的六项结构信号全部可由代码测出。把它们交给 LLM 判断既慢又不稳定， 还会出现「同一页两次诊断结论不同」的问题——写作链路中已实测到核查器的采样波动。

6.4 诊断结论必须标注证据强度

这一节的设计源自一次真实的判断失误。初版方案里，「JSON-LD 覆盖率为零」被写成 「AI 无从识别实体、指标与内容类型」——但这句话站不住： 大模型读纯文本毫无障碍，JSON-LD 并非 AI 读懂页面的必要条件。

结构化数据的真实作用在检索层而非生成层：实体消歧 （sameAs 显式声明「万悉科技」与「Trendee」是同一主体）、 知识图谱收录、特定内容抽取（FAQPage 使问答对可直接提取）。 而它对 AI 检索管线的加权作用，目前没有任何公开确证—— 行业里大量「GEO 最佳实践」其实是从 SEO 直接搬来的推测。

但换一个判据，这条诊断就成立了

品宣稿 P29《2.2 GEO-原生网站基建能力》原文： 「网站通过结构化数据格式（JSON-LD）、内部知识图谱建立……让AI快速抓取、 理解并引用网站核心内容」，并声称带来三项效果：RAG检索速度提高、提升AI引用率、AI理解准确度提升。

而万悉官网 52 个页面，JSON-LD 覆盖率为 0。 这就不再是「我认为你该加 schema」，而是「按你们自己写的标准，官网没做到」—— 判据来自客户自述，无法被反驳，除非承认自己的方法论有问题。

因此 GeoAuditor 的每条结论都必须标注证据档位：

档位判据来源说服力实例
A 档 客户自述标准 品宣稿（知识库语料） 最强，不可反驳 JSON-LD 缺失——违反 P29 自述的核心能力
B 档 可观测事实 纯代码扫描 强，可复现 title 52 页→1 种；718 个标题标签结构健全
C 档 行业推测 通行做法，无公开确证 弱，须标注为建议 alt 文本对 AI 理解的影响
这是两条链路真正的咬合点

A 档判据意味着：用品宣稿知识库作为审计标准，去审这家公司的官网。 两条链路不是并列的两件事，而是一套互相咬合的系统—— 品宣稿定义了「这家公司认为 GEO 该怎么做」，官网则是「它自己做到了多少」。

实现上，agents/standard.py 读取知识库产出的 chunks.jsonl 作为标准库；未构建知识库时自动降级为仅 B/C 档诊断。

同一个错误犯了两次

「title 全站同质 = AI 读不懂页面」与「无 JSON-LD = AI 无从识别实体」， 是同一类错误的两次发作：把 SEO 清单条目当作 GEO 事实断言。 两次都是被追问「凭什么」之后才发现证据不足。 证据分档机制正是为了让这类错误在输出层就被拦住—— C 档结论必须显式标注为推测，写不出判据的条目根本进不了报告。

最后一个维度是本方案独有的

「问题覆盖度」由 QueryGenerator 生成客户问题、再回头比对官网是否作答， 形成闭环检验。这也是四个 Agent 必须齐备的实际理由—— 少了问题生成，诊断就只能停留在结构层面，无法回答「客户想知道的，官网讲了没有」。

08路由与调度

把一句话变成执行计划

这是「简单写多个 Prompt」与「真正的调度」之间的分界。 本方案的关键主张是：路由的产物不是「选中一个 Agent」，而是一份有序的执行计划。

路由的三层结构

沿用写作链路中已验证的分层思路：确定性任务交给代码，只在必要时调用模型。

层适用场景实现成本
① 规则匹配 「官网表达了什么」→ 分析
「哪里需要优化」→ 诊断
「用户会怎么问 AI」→ 问题生成		 关键词表 零
② LLM Router 复合问题、模糊表述、规则未覆盖的说法 小调用，输出 Agent 名单 + 理由 一次
③ 依赖补齐 始终执行 递归展开 + 拓扑排序 零
路由结果必须可解释

执行计划中每个 Agent 都附带被选中的理由（规则命中哪个关键词、 或 LLM 给出的判断、或「作为 X 的前置依赖被补齐」）。 Demo 中这些理由会直接展示——让人看见系统是怎么想的，而不只是它做了什么。

09整合收口

能力形状的产出，问题形状的答案

前面四个 Agent 的输出结构由各自的职责决定：GEO 诊断永远输出那四个小节， 内容策略永远输出三个优先级档。它们是能力形状的。 而用户的问题是任意形状的——一句话可能问两件事，措辞还各不相同。

把链路最后一个 Agent 的输出直接当答案，等于答非所问。 问「哪些内容适合被引用，并给出优化建议」，只答了后半问； 问「GEO 和 SEO 的区别」，却把官网信息分析那固定的七个小节整份倒给用户。 Agent 只有一个，不代表小节只有一节。

它是编排器的固定动作，不是第五个 Agent

整合环节不参与路由，不出现在能力目录里，用户点名也调不到。 这是有意的：前四个是「能力」，由用户需求决定要不要跑； 本环节是编排器的收口动作（map-reduce 里的 reduce），只要跑了 Agent 就自动追加。

单个 Agent 时也要跑——曾按「只有一份材料，整合无意义」跳过， 那是旧设计的残留：当时本环节做的是重写，一份材料确实无需重写； 现在它做的是对齐，而对齐与材料有几份无关。 连续追问时也必须重跑：上游结果可以复用， 但「回答的是哪个问题」每轮都变了。

取材范围限定在本轮计划内

追问时 Blackboard 上留着历轮产出，但「板上有什么」与「这一轮该拿哪些作答」 是两件事。初版把两者混成同一个 bb.results，于是出现过这种自相矛盾： 追问「GEO 和 SEO 有什么区别」，执行计划里只有官网信息分析一个环节、 界面也写着「1 个上游 Agent」，最终答案却标着「原样取自：GEO 诊断」—— 那是上一轮留在板上的。

因此编排器每轮把 plan.agent_names 写进 Blackboard.scope， 收口环节只从范围内取材。缓存复用与取材范围是两个正交的机制： 前者决定「要不要重跑」，后者决定「答案能引用谁」， 混为一谈就会让复用把上一轮的内容带进这一轮的答案。

关键设计：模型只出对照表，正文由代码原样搬运

初版让模型读完全部材料自己写答案，连续踩了三个坑—— 绕过专责环节自己重新推导建议、把优先级分档拍平、上游明明有 2 条只保留 1 条。 每次都靠往 Prompt 里加约束去堵，每次都堵不住。

原因是「原样搬运」根本不是生成任务。 模型每复述一遍就有一次改写和丢失的机会，而这种丢失是静默的： 用户看到的是一份残缺的清单，却不知道自己少看了什么。 沿用写作链路已验证的分工——凡能确定性裁决的，就不该交给模型：

谁做做什么出错时的表现
模型 对齐：用户问的这件事，该由哪个环节的哪个小节回答 选错小节——看得见、可核对
代码 搬运：把那个小节整段原样取出 结构上不可能漏条目或改措辞

模型的全部产出只是一张指针表，一个字正文都不写： 

模型输出的全部内容——一张对照表
## 哪些内容适合被 AI 引用
@采用 geo_auditor / 可被AI引用的内容

## GEO 优化建议
@采用 content_strategist / 高优先级
@采用 content_strategist / 中优先级
@采用 content_strategist / 低优先级

代码据此逐条组装，正文一律从上游产出中原样取出，并标注出处： 

## 哪些内容适合被 AI 引用

**可被AI引用的内容**
- [B档] /geo-center/reports/iresearch-…：艾瑞咨询 2026 GEO 权威报告提到
  万悉科技 Trendee 的「LLM-原生」GEO 技术体系 —— 可回答：…
- [B档] /blog/overseas-geo-multilingual-content-ai-search：…
↑ 原样取自：GEO 诊断
这样一来，三类错误在结构上就不可能发生

漏条目、改措辞、丢 [A档] 标记——都不需要任何 Prompt 约束去防。 剩下唯一可能的错误是「选错小节」，而它摆在明面上，一眼能核。

目录里必须带内容预览

初版给模型的对照清单只列小节名，结果追问「传统 SEO 与 GEO 的区别是什么」时 判成「未覆盖」——可答案就在「可被AI引用的内容」那一节里。

原因是小节名是按能力职责起的，不是按用户会问什么起的， 光看名字无从判断相关性。因此清单里每节都附一段内容预览， 让模型按内容对齐。产出仍然只是指针，正文照样由代码原样搬运。

10咬合点

三处咬合：两条链路如何互相供给

① 审计标准：拿品牌自己的方法论去审它自己

诊断官网最难的不是找问题，是让结论站得住。初版写「官网无 JSON-LD，AI 无从识别实体」—— 这站不住，大模型读纯文本毫无障碍，JSON-LD 对 AI 检索管线的加权作用并无公开确证。

换判据之后

品牌方自己的方法论把 JSON-LD 列为 GEO 网站基建的首要能力 （品宣稿 P29），而官网 52 页覆盖率为 0。

这不是「我建议你加 schema」，而是「按你们自己写的标准，官网没做到」—— 除非承认方法论有问题，否则无法反驳。实测抽出 4 条标准，升格 3 条结论为 A 档。

② 原文问答：补上一条本该存在的路径

四个分析型 Agent 都是「通读全站 → 输出固定小节」的形态，答不了指向具体内容的问题。 问「GEO 和 SEO 有什么区别」时，路由只能指向官网信息分析，而它的八个小节里没有一节是 「官网对某个概念是怎么讲的」——答案就在已抓取的页面里，系统却没有路径把它取出来。

补上这条路径需要的正是检索能力，而知识库链路已经有一套实测过的混合检索。 把它指向站点语料，缺口即被填上：检索定位到具体小节 → 模型据此作答 → 标注页面 URL 供人核对。

③ 策略回灌：让建议变成可发布的初稿

写不了的要说清为什么写不了

13 条策略建议里有 3 条被主动跳过：两条「案例页」因知识库没有客户案例的细节事实， 硬写只会得到泛泛之谈；一条「元数据修改」根本不是文章，是改 meta 标签的工程任务。 把不可写的项也塞进流水线，只会得到一堆需要人逐句删改的稿子，那比不生成更糟。

11工程判断

确定性优先，以及它的五次应用

应用处本可以交给模型改为代码裁决后
引用编号校验（第 3 层）让模型自查引用对不对比对本次证据集，编号不存在即判捏造
数字比对（第 3.5 层）让核查器判断数字是否属实逐字比对语料，无漏报、无采样波动
结构扫描（B 档诊断）让模型看页面判断结构好坏title 唯一性、JSON-LD、h1 数、alt 缺失率直接测
依赖补齐与排序让模型决定先调用谁静态声明 + 递归展开 + 拓扑排序
大纲小节数校验相信模型遵守 Prompt 里的数量约束按规格区间校验并重试一次
最后一条是跑了两次才发现的

同一条 FAQ 指令两次规划，一次 7 个问题、一次 3 个，而规格明写「6–10 个问题」—— 模型违反了自己收到的约束，而系统毫无察觉，直接拿 3 节的大纲跑完了整条链路。 数量是纯确定性判据，本就不该由模型裁决。

处置强度也需要判断：重试一次而非报错。小节偏少只影响完整度不影响正确性， 为此中断整条链路不值当；重试仍不达标就带警告继续，把判断留给人—— 与第 3.5 层「标出来交给人」的处置一致。

为什么不用 LangChain / LlamaIndex / CrewAI

  1. 幻觉控制是本方案重心，而这是框架封装最薄的一环。 四层半里三层是自写的确定性校验，用框架反而要绕开它的默认链路。
  2. 「大纲先行、分节检索」不是框架的默认形态。 RetrievalQA 是一次检索一次生成，要改成每节自带查询各自检索，等于绕过框架自己编排。
  3. 调度逻辑本身就是要展示的东西。DAG 只有 6 个节点、依赖静态可知， Agent 基类约 90 行、路由约 130 行。用框架的 Crew/Graph 把调度包起来， 展示出来的是「会配置框架」而非「会设计调度」。
  4. Prompt 需要逐字可控。四种内容类型的结构规范要分别注入大纲与生成两个 Prompt， 框架的模板层反而是阻碍。

不用框架不等于不会用框架——这是规模判断，不是能力边界。

输出一律行式，不用 JSON

实测本项目所用模型在嵌套结构上不可靠（漏方括号、吐垃圾片段）， 而 ## 小节名 + 每行一条的记录块式文本解析确定且零失败。 这条结论先在写作链路得到验证，后被 Agent 链路沿用。

关键约束

DeepSeek 官方 API 无视觉能力。 deepseek-chat 与 deepseek-reasoner 均为纯文本模型，DeepSeek-VL2 仅开源权重、官方 API 不提供。 而本方案的核心恰是视觉转写，因此该环节必须由通义千问 VL 承担。

按环节分别选型

五个环节对模型的要求差异很大——生成要中文文笔，核查要判定精度，意图解析只抽两个字段。 全流程共用一个模型是浪费，也是短板。因此做了一次固定大纲与证据、仅换生成模型的 A/B：

DeepSeek 与通义（兼容模式）均提供 OpenAI 兼容接口，因此统一用 openai SDK， 仅切换 base_url。换供应商只改配置，不动业务代码。

实测 · 大纲与核查改用行式格式，不用 JSON

qwen-max 在「数组 → 对象 → 数组」三层嵌套上系统性失败： 每个小节都会漏掉 queries 的方括号并吐出 : "heading: " 之类的垃圾片段。而查询原文本身又常含全角冒号与引号 （照抄自资料标题），进一步加剧转义负担。

容错解析与校验重试都只是治标。最终改为行式格式 + 确定性解析 （TITLE: / ## 小节 / Q:），零失败。 这与视觉转写采用小节式文本的成功经验一致：该模型在自然语言结构上可靠， 在深层嵌套 JSON 上不可靠。事实核查的记录块格式同理。

JSON Mode 注意事项

DeepSeek 与通义的 JSON mode 只保证「输出是合法 JSON」，不保证符合你的 schema。 因此每次结构化输出都需 Pydantic 校验，失败则携带错误信息重试一次。 该 retry 逻辑封装为装饰器全项目复用。

依赖版本必须锁定

开发机为 Intel Mac（x86_64），PyTorch 在 2.2.2 之后已停止支持该平台， 而 2.2.2 又要求 numpy<2、transformers<4.45。 直接 pip install sentence-transformers 会装到不兼容组合并在导入时报 NameError: name 'torch' is not defined。实测可用组合： numpy 1.26.4 / torch 2.2.2 / transformers 4.44.2 / sentence-transformers 2.7.0。

为什么不用 LangChain / CrewAI / AutoGen

这几个框架是同类任务的常见默认选择，因此不用它们需要给出理由， 而不是默默略过。以下三条中，第三条是写作链路中实测得出的。

理由说明
① 框架会把被考察的东西藏起来 本链路最该被看见的正是「用户输入路由与 Agent 调用逻辑」。 若使用 CrewAI，路由与依赖编排发生在框架内部——展示出来的是「会配置框架」， 而非「会设计调度」。「必须体现 Agent 调度逻辑」这条要求， 要的恰恰是把调度显式写出来给人看。
② Demo 需要展示执行计划与选中理由 框架的抽象层使「为什么选中这个 Agent」「依赖如何补齐」难以取出并渲染。 手写实现中，执行计划本身就是一个可直接打印的数据结构。
③ 本项目所用模型在嵌套结构化输出上不可靠 这是实测结论：写作链路中 qwen-max 在「数组→对象→数组」 三层嵌套 JSON 上系统性失败（每次漏方括号并吐出垃圾片段）， 最终改用行式格式才稳定。而主流 Agent 框架高度依赖 function calling / JSON schema 驱动工具调用与结构化返回—— 把一个已知在此不稳的模型放进重度依赖它的框架里， 是在已知的坑上盖房子。
成本对照：手写编排约 260 行

base.py（Agent 基类 + Blackboard）约 80 行、 router.py（三层路由 + 依赖解析 + 拓扑排序）约 120 行、 orchestrator.py（按序执行 + 结果收集）约 60 行。

换来的是每一步都可打印、可调试、可在 Demo 中展示。 DAG 只有 4 个节点，引入框架的抽象成本高于它节省的代码。 写作链路未使用 LangChain / LlamaIndex 也是同一判断—— 在这个规模下，框架的抽象成本高于收益。

但必须主动说明，不能默默偏离

不用框架不等于不懂框架。既然框架是常见默认选择， 偏离而不解释是最差的做法——容易被直接理解为「不会用」。 因此本节的三条理由会同样写入 README 的「技术选型说明」， 把一个潜在减分项转为对工程判断力的展示。

一个不做向量检索的决定

全站 9.6 万字，接近知识库语料的三倍，但仍未引入向量检索。 理由是任务形态不同：Agent 要做的是「通读全站得出整体判断」， 而非「找到相关片段回答问题」。分析类任务对全局覆盖的需求高于对精确召回的需求。 若后续语料继续增长至无法一次装入上下文，再引入按板块分批 + 摘要聚合。

12交互

Demo 要把过程摊开

命令行与网页对话框两者都做，重点在可见性—— Demo 的价值不是「能出结果」，而是「让人看见系统怎么决策」。

界面区域展示内容为什么必须展示
对话框自然语言提问，支持连续追问自然语言是最低门槛的入口
执行计划面板选中的 Agent、各自被选中的理由、执行顺序调度是本链路的核心，藏起来等于没做
Agent 时间线逐个 Agent 的执行状态与耗时让「协作」成为可见的事实而非声称
中间结果标签页每个 Agent 的完整输出中间结果是判断系统有没有真在协作的唯一凭据
整合结果最终建议 / 问题清单，结构化呈现最终答案要能对齐回用户实际问的那个问题
结构扫描面板确定性指标的实测数值与判定结论的档位依据必须可追溯
13不足

已知边界与后续方向

按影响排序。第一条是当前最危险的，因为它绕过了全部拦截机制。

不足影响后续方向
视觉转写质量无法自动校验 模型若把图表里的数字看错，下游全部环节继承该错误，而四层半拦截查不出来——它对照的正是这份已经错了的语料 对含数字的页做双模型交叉转写，不一致处标记待人工确认
第 3.5 层分不清推算与编造 跨证据做加法得到的正确数字会被判为编造 对 missing 的数字追加一次「能否由证据中的数经简单运算得到」的定向检查
评测集仅 25 条人工标注 高难度集单条权重 11%，一次标注错误明显移动分数 扩到 50+ 条，补跨页论述与多跳问题
大纲只校验数量，不校验覆盖面 7 个问题也可能全都围着同一件事打转 比对大纲与资料库目录的覆盖度，对未被触及的章节给出提示
知识库仅支持单文档 多文档需要引用格式带文档标识与跨文档证据冲突处理 站点语料侧已走通多语料抽象，知识库侧照此跟上
Agent 依赖为静态声明 无法按问题动态调整依赖强度 引入可选依赖：上游证据已充分时跳过前置环节
客户问题生成无真实验证 生成的问题是模型模拟，未与真实搜索数据比对 接入真实 AI 平台提问测试，验证官网是否真的被引用
抓取为单次快照 官网更新后需手动重抓 记录 ETag / Last-Modified 做增量更新与变更对比

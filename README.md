# 品牌知识库 RAG 内容生成与多 Agent 协作系统

把一份品牌品宣 PDF 变成可检索、可引用的知识库，在其上做两件事：
**生成每句话都能溯源到页码的营销内容**，以及**由多个 Agent 协作诊断官网的 AI 可见性（GEO）并给出内容策略**。

两条链路共享同一个知识库与同一套混合检索，因此形成一条闭环：

```
  品宣 PDF  ──→  知识库语料 ─┐
                             ├─→  混合检索（一套检索，两份索引）
  官网 52 页 ──→  站点语料 ─┘
                                        │
                    ┌───────────────────┴───────────────────┐
                    ↓                                       ↓
              内容生成                                多 Agent 协作
         页码引用 · 四层半拦截                    官网诊断 ─→ 内容策略
                    ↑                                       │
                    └──────────── ③ 策略回灌 ───────────────┘

  三处咬合：
  ①  知识库 ─→ 审计标准 ─→ GEO 诊断      让结论有「品牌自己的方法论」作判据
  ②  站点语料 ─→ 原文问答 Agent           补上「官网上这件事怎么说的」这条路径
  ③  内容策略 ─→ 写作链路                 建议直接变成可溯源的初稿
```

> **完整技术方案：[`docs/技术方案.html`](docs/技术方案.html)** —— 13 节 / 16 图，
> 从数据基线、解析策略、检索评测、幻觉控制到 Agent 调度与工程取舍，
> 本 README 是它的摘要版。

三处实测结果：

| | |
|---|---|
| **0.741 vs 0.593** | 高难度查询集上混合检索的 MRR 对纯向量（Hit@1 66.7% vs 44.4%），BM25 一路的价值由此成为实测结论 |
| **4 → 3** | 从品宣稿抽出 4 条品牌自述标准，据此把 3 条诊断结论升格为「按你自己的方法论应做到而未做到」|
| **4/4** | 四份内容样例的引用编号全部有效——第 2、3 层为纯代码校验，捏造的 `[Pxx]` 会被检出并在界面标红 |

> 分析对象为一家真实的 GEO 服务商，其品宣稿与官网内容仅用于本项目的技术验证。
> 仓库不包含 PDF 原件与官网抓取全文，二者均可由脚本重建（见 §2）。

## 一、两条链路的三处咬合

两条链路是同一条内容运营流水线上的两段，共享同一份知识库与同一套检索。
它们之间有三处互相供给的接口，每一处都解决一个单条链路无法自足的问题：

**① 审计标准来自品牌自己的方法论（`agents/standard.py`）**

诊断官网最难的不是找问题，是让结论站得住。初版写「官网无 JSON-LD，AI 无从识别实体」——
这站不住，大模型读纯文本毫无障碍。换成从品宣稿里抽出的自述标准之后结论才立得住：

> **品牌方自己的方法论把 JSON-LD 列为 GEO 网站基建的首要能力（品宣稿 P29），
> 而官网 52 页覆盖率为 0。**

这不是「我建议你加 schema」，而是「按你们自己写的标准，官网没做到」——除非承认方法论有问题，否则无法反驳。
实测抽出 4 条标准，升格 3 条结论为 A 档。

**② 原文问答（`agents/site_qa.py`）**

四个分析型 Agent 都是「通读全站 → 输出固定小节」的形态，结构上答不了指向具体内容的问题：
问「GEO 和 SEO 有什么区别」，它们的固定小节里没有一节承担「官网对某个概念怎么讲」。
这类问题需要的是检索，而不是又一个分析器——因此把混合检索指向站点语料，单设一个问答型 Agent。

**③ 策略回灌写作链路（`writer/from_strategy.py`）**

内容策略产出「应补一篇 FAQ 回答『如何让 AI 推荐我们的产品』」，然后就停了。
接上写作链路，这条建议直接变成初稿——而且因为写作链路只能引用知识库里的内容并要过四层半拦截，
**产出的不是「AI 编的一篇稿子」，而是只由品牌方已公开事实组装、每句话可溯源到页码的初稿**。

## 二、快速开始

### 环境

Python 3.12（3.10+ 应可运行，未验证）。

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

依赖版本区间是实测结果，**不可随意放宽**，原因写在 `requirements.txt` 里：
开发机为 Intel Mac，PyTorch 于 2.2.2 后停止支持该平台，连带约束了 numpy 与 transformers。

首次运行会自动下载 Embedding 模型 `bge-small-zh-v1.5`（约 95MB）。

### 配置

需要一个**阿里云百炼（DashScope）**的 API Key：

```bash
cp .env.example .env    # 编辑 .env，填入 DASHSCOPE_API_KEY
```

**不配 key 也能跑的部分**：PDF 解析、切分、索引构建、检索验证、检索评测、
官网抓取、确定性结构扫描、A 档标准抽取、规则路由——全部零 API 调用。
只有视觉转写与需要模型判断的环节需要 key。

### 数据准备

仓库随附**知识库**的衍生产物（`data/chunks.jsonl`、`data/faiss.index`），克隆后即可跑通写作链路。
**站点语料不入库**——它重建免费且一分钟内完成，没有理由把另一家公司的官网正文放进版本库：

```bash
# 官网语料：零 API 成本，约 1 分钟。跑 Agent 链路前需要先执行
python -m website.fetch          # 抓取全站 → data/site_pages.jsonl
python -m website.chunk          # 按 h2 分节 → data/site_chunks.jsonl

# 知识库：仅在 chunks.jsonl 缺失时需要，视觉转写是唯一付费步骤
python -m kb.parse               # 文字层提取 + 页面渲染，零 API 成本
python -m kb.vision              # 视觉转写 42 页（支持断点续做）
python -m kb.chunk               # 切分为检索单元

# 两份语料各建各的索引，本地模型，零 API 成本
python -m retrieval.build_index
```

### 运行

```bash
# 网页 Demo
streamlit run apps/app_writer.py    # 内容生成：引用溯源与四层半拦截逐层摊开
streamlit run apps/app_agents.py    # 多 Agent 协作：执行计划与中间结果全程可见

# 命令行
python -m apps.cli "请分析官网目前哪些内容适合被 AI 引用，并给出 GEO 优化建议"
python -m apps.cli -i                                    # 连续追问，已完成环节复用缓存
python -m writer.generate "为什么中国出海品牌需要进行GEO优化"
python -m agents.site_qa "GEO 和 SEO 有什么区别"          # 原文问答
python -m writer.from_strategy --plan                    # 策略 → 成稿
```

### 单独运行各环节

```bash
python -m retrieval.eval --all --hard          # 检索评测，零 API 成本
python -m retrieval.search "什么是GEO" --compare # 对比向量/BM25/融合三路
python -m retrieval.search "GEO和SEO的区别" -c site  # 在站点语料里检索
python -m agents.router "官网哪里需要优化" --no-llm  # 只看路由结果，不执行
python -m agents.scan                          # 确定性结构扫描
python -m agents.standard                      # 从品宣稿抽取 A 档审计标准
python -m writer.verify "主题"                  # 第 4 层事实核查
python -m writer.literal article.md            # 第 3.5 层数字校验
```

## 三、知识库链路

### 把 PDF 变成可引用的知识资产

```
PDF ──┬─→ 文字层提取（PyMuPDF）──┐
      │                          ├─→ 每页两路并存 ─→ 切分 ─→ 向量索引 + BM25
      └─→ 页面渲染 ─→ 视觉转写 ──┘
```

**为什么必须双通道**：品宣稿是设计稿，信息大量藏在图表、流程图、数据看板里。
实测文字层仅 **10,738 字**，视觉转写 **21,317 字**——约三分之二的内容只有视觉通道能拿到，
其中 P8、P34 两页文字层近乎为空，完全依赖视觉。

**阅读顺序恢复**：PDF 文字块的存储顺序不等于阅读顺序。品宣稿常见「三栏卡片」排版，
按存储顺序直接拼接会把三栏的第一行串成一句。因此先按视觉行分组，行内从左到右、行间从上到下重排。

**切分以页为单位**：幻灯片本身就是设计好的语义块，**页码天然是引用锚点**。
在此之上识别分节页（带大号装饰序号、自身几无内容）并入其后一页，避免产生「只有一个标题」的噪声 chunk；
把分节页标题作为章节名向后传播。42 页 → 39 个 chunk，其中 38 个入索引。

### 大纲先行，分节检索

```
一句话指令 ─→ 意图解析 ─→ 大纲规划 ─→ 分节检索 ─→ 生成 ─→ 四层半核查
             类型+主题     每节自带查询   节内 RRF     带引用
```

这是本方案与朴素 RAG 的主要差别。朴素做法用主题做一次检索，所有小节共享一份证据集，
结果是每一节都不精准。这里先规划大纲，**每个小节自带 2–3 条查询各自检索**，节内再用 RRF 融成一份排序。

关键设计：**把资料库目录一并交给规划器**。模型看得见资料的实际标题措辞，
才能把「怎么衡量效果」这类宽问题改写成「AI可见性监控 追踪指标」——这正是纯语义检索跨不过去的鸿沟。

## 四、混合检索

向量（bge-small-zh + FAISS）+ BM25（jieba 分词），用 **RRF** 融合而非加权求和：
余弦相似度落在 [0,1]，BM25 分数无上界且随语料波动，两者量纲不同；
RRF 只看**排名**不看分数，无需调权重、无需归一化。

检索层不认识具体的 chunk 类型，只依赖 `retrieval/corpus.py` 里的 `Indexable` 协议，
因此同一套检索同时服务两份语料：

| 语料 | 来源 | 单元数 | 引用锚点 |
|---|---|---|---|
| 知识库 | 品宣 PDF 42 页 | 38 | 页码 `[P29]` |
| 站点 | 官网 52 页 / 96,327 字 | 193 | 页面 URL |

**两份语料不混进一个索引**：检索出一条证据却分不清该标页码还是标 URL，引用溯源就失去意义。

BM25 用 `rank_bm25`，**全量内存打分、不落盘，也没有倒排表**——O(N×|query|) 扫全库。
当前 38 / 193 条语料下建索引 0.5 秒、单次检索 0.4 毫秒，引入倒排结构无收益；语料上到十万级则必须换掉。

站点语料按 **h2 分节**而非按页切——网页是连续文档，整页一个 chunk 能命中却指不出「答案在哪一段」。
首页 3,508 字、62 个标题，其中就含「GEO 与 SEO 的区别」那组 FAQ；整页成块时它被淹没，按节切开后可直接命中。

### 评测

`python -m retrieval.eval --all [--hard]`

**基础集（16 条，查询与页标题接近）**——三路 Hit@5 全部 100%，混合与纯向量完全相同：

| 检索方式 | Hit@1 | Hit@5 | MRR |
|---|---|---|---|
| 向量 (bge) | 93.8% | 100.0% | 0.969 |
| BM25 | 81.2% | 100.0% | 0.896 |
| 混合 (RRF) | 93.8% | 100.0% | 0.969 |

**这组数字看不出混合检索有没有价值**，而一个满分的评测集比没有评测更危险——
它会让人得出「BM25 可以删掉」的错误结论。因此补了第二组，刻意贴近真实写作场景：
主题式宽问题（与任何标题都不字面重合）+ 专名查询。

**高难度集（9 条）**——混合严格优于两条单路：

| 检索方式 | Hit@1 | Hit@5 | MRR |
|---|---|---|---|
| 向量 (bge) | 44.4% | 88.9% | 0.593 |
| BM25 | 33.3% | 88.9% | 0.511 |
| **混合 (RRF)** | **66.7%** | **88.9%** | **0.741** |

Hit@1 是次优者的 1.5 倍。**BM25 这一路的价值到这里才成为实测结论，而不是理论推演。**

## 五、幻觉控制与引用溯源

内容生成的第一约束是不得编造知识库中没有的公司事实、客户案例、数据或技术指标。
单靠 Prompt 约束做不到，因此设了四层半，**其中三层是纯代码、零 API 成本、零波动**：

| 层 | 做什么 | 实现 | 成本 |
|---|---|---|---|
| **第 1 层** | Prompt 硬约束 | `prompts/writer/generate.md` | — |
| **第 2 层** | 引用格式解析——正则抽出全文 `[Pxx]`，定位到具体句子 | `writer/generate.py` | 纯代码 |
| **第 3 层** | 引用有效性校验——比对本次证据集，编号不存在即判捏造 | `writer/generate.py` | 纯代码 |
| **第 3.5 层** | **数字确定性校验**——量化表述逐字比对语料 | `writer/literal.py` | 纯代码 |
| **第 4 层** | LLM 事实核查——逐条抽出事实性陈述，对照全部证据判定 | `writer/verify.py` | 一次调用 |

### 为什么单设第 3.5 层

1. **数字是幻觉最危险的载体。** A/B 实测中，`deepseek-v3` 把证据里的「61.66 亿」写成「80 亿」，
   并凭空造出「300%」——句子读起来专业、还挂着真实的引用编号，人眼极难发现。
2. **LLM 核查器对数字不可靠。** 实测同一篇文章两次核查结果不同（1 条 vs 5 条），存在采样波动。
3. **这件事本不需要模型。** 数字要么在语料里逐字出现，要么没有。`in corpus` 一次判定，
   零成本、零波动、无漏报——**凡能用确定性方法裁决的，就不该交给模型**。

### 生成模型的选型也是幻觉控制的一部分

固定大纲与证据、仅换生成模型的 A/B 实测：

| 模型 | 表现 |
|---|---|
| `qwen-max` | 套话多，且违反 Prompt 明令禁止的「本文将探讨」句式 |
| **`qwen3-max`** | **开篇即上带引用的硬事实，事实纪律良好** ← 选它 |
| `deepseek-v3` | 文笔最佳，但把 61.66 亿写成 80 亿、凭空造出 300% |

**第一优先级是不得编造数据，因此选事实纪律而非文笔。** 配置在 `core/llm.py` 的 `Provider.task_models` 里，
改模型不动业务代码。

## 六、多 Agent 协作

### 五个能力 Agent + 一个收口环节

| Agent | 职责 | 依赖 | 依赖的理由 |
|---|---|---|---|
| `site_analyst` 官网信息分析 | 品牌定位、产品能力、技术关键词、服务对象、信息缺口 | — | DAG 根节点 |
| `site_qa` 原文问答 | 检索官网原文作答并标注 URL 出处 | — | 走检索，不需要品牌基线 |
| `geo_auditor` GEO 诊断 | 哪些内容可被引用 / 会被忽略 / 会被误解 / 缺什么 | `site_analyst` | 没有品牌基线，无法判断表达是否偏离 |
| `query_generator` 用户问题生成 | 按认知—评估—决策三阶段模拟客户提问 | `site_analyst` | 客户会问什么取决于这家公司卖什么、卖给谁 |
| `content_strategist` 内容策略 | FAQ / Blog / 案例页 / 产品说明的补充建议与优先级 | `geo_auditor`<br>`query_generator` | 诊断只说缺什么，不说客户想看什么 |
| `synthesize` 整合收口 | 把能力形状的产出对齐回问题形状 | — | **不参与路由**，编排器固定追加 |

### 两类输入：分析吃摘要，问答吃检索

六个环节的输入只有两种来源，分野在**任务形态**而非实现难度：

- **四个分析型 Agent** 吃「全站摘要 + 上游产出」。全站 96,327 字装不进一次 Prompt，
  按「覆盖优先」压到 30,000 字：全站 h1–h3 大纲 62%（让 51 页全部露面）、
  品牌身份页正文 15%（要原话，摘要会变味）、各板块 3 篇正文样本（判断表达方式）。
- **只有原文问答** 吃混合检索的 top-5 小节。

问「官网品牌定位是什么」要的是通读全站的整体判断，给 top-5 等于让模型基于 5 段内容评价 51 页；
问「GEO 和 SEO 有什么区别」要的才是精确定位。**检索与全局摘要解决的不是同一类问题。**

### 调度三层

```
① 规则匹配      词组共现 → Agent           零成本、零延迟
② LLM Router    复合与模糊问题才触发        一次小调用
③ 依赖补齐      递归展开 + 拓扑排序         纯代码，确定性、可复现
```

第 ③ 层是关键：用户只说「该补充什么内容」，规则命中内容策略，
而它依赖 GEO 诊断与用户问题生成，二者又都依赖官网信息分析——
**用户提一个需求，系统排一条流水线。** 每个环节都附带被选中的理由，Demo 中直接展示。

五条路由映射实测：

```
官网表达了什么       → 官网信息分析
GEO 和 SEO 有什么区别 → 原文问答
哪里需要优化         → 官网信息分析 → GEO 诊断
用户会怎么问 AI      → 官网信息分析 → 用户问题生成
应该写什么内容       → 官网信息分析 → GEO 诊断 → 用户问题生成 → 内容策略
```

### 追问缓存的正确性

连续追问时编排器复用板上已有结果，前提是**该 Agent 的产出与用户问什么无关**。
分析型 Agent 满足这一点；原文问答与整合收口不满足——它们的输入里就含用户的问题。
这条判据声明在 `Agent.question_dependent` 上而非硬编码在编排器里，新增 Agent 时如实声明即可，
调度与界面自动跟上。

### 证据分级

诊断结论一律标注可信度来源：

| 档位 | 判据 | 可靠性 |
|---|---|---|
| **A 档** | 与品牌品宣稿自述标准冲突 | 判据出自品牌自己的方法论 |
| **B 档** | 纯代码扫描出的可观测事实 | 可复现 |
| **C 档** | 行业推测，无公开确证 | 仅供参考 |

## 七、技术选型说明

### 为什么不用 LangChain / LlamaIndex / CrewAI

1. **幻觉控制与引用溯源是重心**，而这是框架封装得最薄的一环。四层半拦截里有三层是自写的确定性校验，
   用框架反而要绕开它的默认链路。
2. **「大纲先行、分节检索」不是框架的默认形态。** `RetrievalQA` 是一次检索一次生成，
   要改成每节自带查询各自检索，等于绕过框架自己编排。
3. **调度逻辑本身就是要展示的东西。** DAG 只有 6 个节点、依赖静态可知；
   `base.py`（Agent 基类 + Blackboard）约 90 行、`router.py`（三层路由 + 依赖解析 + 拓扑排序）约 130 行。
   用框架的 `Crew`/`Graph` 把调度包起来，等于把最该展示的部分藏进黑盒。
4. **Prompt 需要逐字可控。** 四种内容类型的结构规范要分别注入大纲与生成两个 Prompt，
   框架的模板层反而是阻碍。

不用框架不等于不会用框架——这是规模判断，不是能力边界。

### 为什么本地 Embedding 而非云端 API

克隆仓库后无需配置任何 key 即可跑通检索与评测，把「要花钱才能验证」这道门槛从检索链路上彻底移除。
`bge-small-zh-v1.5` 仅 ~95MB，中文语义检索表现足够。

### 输出格式一律行式，不用 JSON

实测本项目所用模型在嵌套结构上不可靠（漏方括号、吐垃圾片段），而 `## 小节名` + 每行一条的
记录块式文本解析确定且零失败。这条结论先在写作链路得到验证，后被 Agent 链路沿用。

## 九、已知不足与后续方向

**1. 第 3.5 层分不清「跨证据推算」与「凭空编造」**

模型写了「全球主流AI网站月访问量合计已超80亿」并标注 `[P08-09]`。
第 3.5 层判为编造（语料中查无「80亿」），第 4 层判为有据支持——两层结论相反。
实际情况是 P08-09 列出了 Top 6 的月访问量（61.66 + 11.82 + … = 83.23 亿），**模型做了一次加法**。
这个数在事实上正确，但确实不是语料里的原话。

当前处置是标出来交给人判断，不自动改写——宁可多报不漏报。
**两层结论矛盾本身不是 bug，而是设计意图**：如果两层永远一致，其中一层就是多余的。

**2. 评测集共 25 条人工标注查询，规模仍偏小**

基础集 16 条已打满 Hit@5 100%，区分度耗尽；高难度集 9 条虽能分出三路优劣，
但单条查询权重高达 11%。后续扩到 50+ 条，并补上跨页论述与多跳问题。

**3. 视觉转写质量无法自动校验**

只能靠 `data/preview.html` 人工逐页抽检。模型若把图表里的数字看错，下游全部环节都会继承这个错误，
而四层半拦截**查不出来**——因为它对照的正是这份已经错了的语料。
后续可对含数字的页做双模型交叉转写，不一致处标记待人工确认。

**4. 知识库切分以页为单位，跨页论述会被切断**

当前靠「章节名向后传播」缓解，但不彻底。后续可引入父子 chunk：检索用页级，喂给模型时带上同章节的相邻页。

**5. 只支持单文档知识库**

`config.SOURCE_PDF` 写死一份 PDF。多文档场景需要引用格式带文档标识（如 `[品宣稿-P12]`）
以及跨文档的证据冲突处理，当前均未实现。站点语料已走通多语料抽象，知识库这一侧尚未跟上。

**6. Agent 依赖为静态声明**

DAG 在代码中写死，无法按问题动态调整依赖强度。后续可引入「可选依赖」——上游证据已充分时跳过前置环节。

**7. 用户问题生成无真实验证**

生成的客户问题是模型模拟，未与真实搜索数据比对。后续接入真实 AI 平台提问测试，
验证官网是否真的被引用。

**8. 抓取为单次快照**

官网更新后需手动重抓，无增量机制。后续记录 ETag / Last-Modified 做增量更新与变更对比。

**9. 身份页路径为硬编码**

`agents/context.py` 的 `IDENTITY_PATHS` 写死四条路径，其中 `/geo-agent` 是本站独有。
换一个站点时它匹配不到任何页面，那 15% 的身份页预算就少分一页——**不报错，只静默少给**。

已验证可由确定性规则替代：先取被 ≥90% 页面指向的全局导航页，再按「路径下无子页面」
区分身份页与板块入口（`/about` 0 个子页 vs `/geo-center` 18 个）。该规则在本站上的
推导结果与手写列表完全一致，尚未实现。

**10. 大纲小节数只做区间校验，不保证内容覆盖面**

同一条 FAQ 指令两次规划曾得到 7 个问题与 3 个问题，而规格明写「6–10 个」——
模型违反了自己收到的约束而系统毫无察觉。现已在 `writer/outline.plan()` 中按
`ContentTypeSpec.min_sections/max_sections` 校验并重试一次（见 `examples/agents/04_策略到成稿.md`）。

但这只解决了「够不够多」，没解决「够不够全」：7 个问题也可能全都围着「什么是 GEO」打转。
后续可比对大纲与资料库目录的覆盖度，对完全没被任何小节触及的章节给出提示。
